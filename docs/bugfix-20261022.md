## 3. 服务器COS故障定位及已执行恢复

主线程在真实服务器核对到：COS挂载存在，但`ensure_diskfree`为`10240MiB`；`/tmp`当时可用约`9.46 × 10^9`字节，低于这项10GiB预留门槛，导致COS FUSE写入EIO。不能把这类运行失败统一归为“图片存储尚未配置”，也不能只凭挂载目录存在就声称写入正常。

已执行的有限恢复：

1. 仅将该缓存预留参数改为`2048MiB`并持久化，不清理用户照片、业务对象或数据库。
2. 使用原业务镜像重新创建API容器，使其绑定恢复后的实际挂载；没有借此升级本批业务代码或执行第20迁移。
3. 用96字节合成PNG执行真实对象写入和读回，校验一致。保留1个诊断对象，本次没有写入业务数据库记录。

该参数是此次服务器条件下的修复结果，不是适用于所有机器的通用默认值。后续仍需监控缓存空间及写失败；任何清理须先列出精确对象/文件清单并取得授权，不执行宽范围删除。诊断对象不是家庭照片，不将其二进制、路径令牌或凭据放入Git。真实微信上传确认与业务保存仍需独立取证。

## 4. 数据库与接口变化

新增迁移：[`202610220001_calendar_event_archive`](../apps/api/prisma/migrations/202610220001_calendar_event_archive/migration.sql)。仅向`CalendarEvent`增加`version Int default 1`和可空`archivedAt`，不改已应用迁移，不删除旧行，不改原创建者、sourceType/sourceId或历史日期。模型总数仍为50，迁移目录总数变为20。

| 路径（省略内部/v1） | 行为 |
| --- | --- |
| `GET /calendar/events` | 旧版独立纪念日增加`legacy:true`、版本及按实际模块权限生成的`canArchive`；保留原source字段；已归档行不再返回 |
| `POST /calendar/events/:eventId/archive` | 仅允许当前家庭、type=ANNIVERSARY、sourceType/sourceId均空、未归档的旧行；验证expectedVersion与共享calendar:EDIT；软归档并写审计 |
| `POST /calendar/anniversaries/:anniversaryId/archive` | 既有新版纪念日归档接口；归档整条定义使各年份投影消失，原共享权限策略不变 |

旧归档接口不能删除餐点、行程、关联投影或其他家庭资源。API专项采用与生产相同的ValidationPipe配置：合法字段转换/白名单过滤，非法版本拒绝；不把测试中的严格管道设置误写成生产拒绝所有未知字段。

升级fixture新增未知创建者的旧纪念日及关联餐点投影，断言新增字段默认值、原数据/来源保留。新增HTTP用例覆盖实际读取、只读拒绝、跨家庭、旧版本409无副作用、共享编辑者归档、审计与日历消失。整菜移除及待办保留停用负责人HTTP路径也已补用例；**本文冻结时这些隔离数据库结果尚未完成，不能记PASS**。
