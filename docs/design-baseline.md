# 扣扣的家设计基线

更新日期：2026-08-31；本轮状态为设计评审稿，未重新验证现网。

## 用户要求与当前工程方案

用户明确要求与乙方建议的来源分类，以[实施契约](design/contract-details.md)为准。以下包含工程方案，不代表用户已确认每个技术细节。

1. 微信只负责账号身份登录；家庭角色、模块权限和行程权限由本系统后台维护。
2. 账号可以拥有多个角色。厨师是餐饮模块的子角色；露营协作者不自动获得所有行程访问权。
3. 只有显式加入某次行程的成员可以访问该行程。完成后保留历史成员关系，使参与者继续查看历史内容。
4. 行李模板完全由用户自定义。系统不内置“烧烤模块”，也不得因为模板名称是“烧烤”而自动填充物品或触发特殊逻辑。
5. 套用模板时复制为 `TripPackingItem` 行程快照；模板后来修改、归档或删除，不改变已生成的行程清单。
6. 一个行程可以套用多个模板并手工追加本次物品；重复套用按来源模板项标识去重。
7. 行李负责人必须是该行程成员；一期准备状态为 `PENDING` 和 `PACKED`。
8. 菜谱不记录难度、忌口和营养；调料不记录用量。
9. 库存比对仅作辅助判断，充足、缺少、未知全部展示并使用不同颜色；用户负责最终确认。
10. 不建设家庭账本、预算、费用分摊或家务积分排名。

## 生产架构

- 客户端：uni-app + Vue 3 + TypeScript。
- API：NestJS + Fastify + Prisma。
- 数据库：PostgreSQL 17；出现真实空间查询需求后再启用 PostGIS。
- 缓存/任务：Redis 7；通知模块启用 BullMQ。
- 对象存储：腾讯云 COS 北京私有桶。
- 边缘入口：Nginx + Certbot。
- 正式 API：`https://pp6v4.com/api/v1`，不新增 `api.pp6v4.com`。
