# 菜谱与露营表单修复（2026-10-21）

客户端修复版：`0.1.1`，versionCode `101`。本批仅修改客户端，没有后端、数据库迁移或服务器部署。

## 用户反馈与处理

| 反馈 | 本批处理 |
| --- | --- |
| 新建菜谱尚未填完就提示必须有菜名、食材、做法 | 新菜选图仅保留本地预览，不调用菜谱创建或上传接口；明确点保存才校验并提交 |
| 菜谱输入框不知道填什么、看不到输入 | 基本信息优先展示；菜名、分类、食材、数量、单位、调料、步骤均有可见标签和示例；数量可空、调料不记用量 |
| 露营、模板等输入框同样难用 | 原生 input 统一明确高度/最小高度 88rpx；本批三个表单移除纵向内边距挤压，路线节点和住宿也补充字段标签与示例 |
| 找不到行李、无法选模板 | 行程详情顶部展示“本次行李”，显式提供手工添加、模板预览与选择按钮，不再依赖首次选中项未变化的 picker 事件 |
| 新建模板与原行程断开 | 从行程进入新建模板，保存后返回同身份的原行程并展示模板选择；用户明确点击后才复制行李，绝不自动套到别的行程 |
| 地图选址后不知道下一步 | 创建表单置于行程列表前，显示已选地点、尚未保存说明和填写日期后保存的指引；创建成功后打开详情并提示准备行李 |

旧交付产物的 input 已包含 placeholder、value 和 bindinput，不是模板编译丢失绑定。但多处 input 使用 border-box、纵向 padding 和边框却没有指定高度，存在原生默认高度不足、文本内容区被挤压的问题。布局修复及 CSS 回归不等于已经在真机确认输入体验。

新菜图片上传失败会保留已创建的草稿 ID 和版本；重试不重复创建菜谱。若图片确认已在服务端生效但响应丢失，保留原 intent/checksum，重试先核对同次确认，再更新文字；只接受该确认应产生的版本递增，不盲目采用其他成员的更新。文字本身提交失败时不再误报“文字已保存”。

历史编辑菜谱的更换封面仍沿用已有即时上传流程，不声称本批将所有旧菜谱封面编辑改成延迟上传。
