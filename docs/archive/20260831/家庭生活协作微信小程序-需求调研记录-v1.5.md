## 调研目标与参与范围

产品主要服务于夫妻二人及家庭成员；朋友属于普通账号，通过管理员授权后，可参与指定功能。朋友的典型场景是参与某次露营协作，或来家里时参与点菜。

| 主题 | 用户诉求 | 建议 | 整理结论（详见U/E来源分类） |
| --- | --- | --- | --- |
| 登录 | 使用微信授权 | 以 wx.login 临时 code 换取 openid；家庭权限由业务后台维护 | 采用微信身份登录，不使用微信昵称头像作为权限依据 |
| 账号 | 至少本人和妻子两个账号，可增加家人和朋友 | 家庭成员关系与微信账号分离 | 账号必须登录后再通过邀请加入家庭 |
| 角色 | 厨师是餐饮子角色；露营是大角色；账号可有多个角色 | 角色提供默认权限，成员权限可覆盖 | 采用多角色叠加及模块 VIEW/EDIT/MANAGE 权限 |
| 菜谱 | 厨师录入分类、食材、调料、图片和做法 | 菜谱结构化、支持上下架 | 不记录难度、忌口；调料不填用量 |
| 点餐 | 两人各自选择某一餐想吃的菜，系统汇总 | 餐点作为聚合容器 | 显示待做菜单和合并后的食材需求 |
| 库存 | 登记家中现有食材和调料，与菜单比对 | 只辅助判断，保留人工确认 | 充足、缺少、未知使用不同颜色，全部展示 |
| 购物 | 记录想买但不急需的东西，下次超市按清单购买 | 同时允许从缺料生成购物项 | 不增加账本、预算和费用分摊 |
| 露营 | 地图、路线、住宿、交通、行李、分工、照片 | 每次行程为独立协作空间 | 只有行程成员可进入；历史成员可继续查看历史行程 |
| 行李模板 | 例如每次烧烤都带固定的一组物品，希望自己定义 | 制作家庭范围可复用模板 | 烧烤只是用户自定义名称；模板和物品完全自定义 |
| 日历 | 展示餐点、纪念日、露营和其他日期事项 | 统一聚合事件但保留来源模块 | 可从日历新建某一餐并跳转来源详情 |
| 待办 | 例如清洗空调，指定负责人并提醒 | 设计负责人、截止时间、状态和提醒 | 保留家庭待办，不扩展成家务积分体系 |
| 扩展 | 收藏灵感、家庭档案、数据看板 | 收藏可转换为业务草稿；看板只做非财务指标 | 纳入设计，不加入家庭账本 |

## 自定义行李模板专项确认

| 问题 | 用户要求及工程建议（详见补充） |
| --- | --- |
| 系统是否内置烧烤模块 | 否。任何模板名称都只是用户数据，系统不识别“烧烤”三个字。 |
| 谁创建模板 | 有露营编辑权限的家庭成员；模板归属家庭，可由创建者或管理员维护。 |
| 模板包含什么 | 名称、说明及任意多条物品；物品可记录默认数量、单位、备注和排序。 |
| 如何用于行程 | 套用时复制为该次行程的独立快照；一个行程可套用多个模板并手工加物品。 |
| 模板修改是否影响历史 | 不影响。已生成的行程行李保持当时内容。 |
| 重复套用 | 按来源模板物品标识去重，返回新增数和跳过数。 |
| 负责人 | 只能选择当前行程成员；有canEdit编辑权限的行程成员可更新准备状态。 |
| 状态 | 一期采用待准备、已准备两态；不把物品类型写成固定业务模块。 |

## 明确排除范围

| 排除项 | 原因与边界 |
| --- | --- |
| 家庭账本、预算、费用分摊 | 当前阶段明确不做，避免引入非目标矛盾和高敏感财务数据。 |
| 家务积分或排名 | 不做游戏化考核；仅保留普通家庭待办。 |
| 忌口、营养、卡路里与菜谱难度 | 用户已明确不需要；不在字段、筛选或看板中出现。 |
| 实时位置追踪 | 地图只展示计划路线与地点，不持续采集成员位置。 |
| 公开社交 | 不做公开露营社区或陌生人内容推荐。 |

V：源码包含登录、家庭、菜谱、餐点、库存、购物、日历、行程和行李模板模块。当前只有访问令牌，没有refresh接口；当前模块权限表不等于所有服务都已实施模块鉴权。下文未实现接口均为目标契约，不是现网API清单。
